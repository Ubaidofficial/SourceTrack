## 2. Four new defect classes

Full entries are `KI-78` … `KI-99` in `KNOWN_ISSUES.md`. The **classes** — the reason these are more
than eleven unrelated bugs:

### 2.1 The right check applied at the wrong layer

`/api/analytics/collect` ran the **reporting-side** bot predicate at **ingestion** (`KI-78`, fixed
#666). Reporting asks *"crawler or human?"*; ingestion must ask *"does this client execute JS?"*.
They disagree exactly where it matters — Googlebot renders JS and must be dropped; an in-app WebView
is a human and must be kept. **This was the 2026-07-14 failure still running**, fixed once at one
call site and never swept.

The sweep that followed found `/sp/e` and `/sp/pixel.gif` metering quota with no filter at all
(`KI-79`, fixed #667) — a **scope accident**, not a decision, so nothing recorded the asymmetry
between proxy and direct customers.

⚠️ **And it found where the sweep must STOP.** `server-events.js` must **never** be bot-filtered
(`KI-80`, DO-NOT-FIX): there is no browser, the UA signal is absent by construction, and a filter
there would drop **real customer conversions**. It is logged as an entry precisely because it looks
identical to the other two from a grep.

### 2.2 Absence of evidence read as evidence of absence

`job_runs` is **not a reliable negative** (`KI-83`). Verified on `main`: its only writers are
`nightly-attribution.js`, `anomaly-watcher.js` and the `api/lib/job-runs.js` helper.
`health-agent.js` and `data-quality-check.js` touch it only through `.select()` **reads** filtered to
`job_name = 'nightly-attribution'`; `proxy-domain-recheck.js` does not reference it at all.

**`data-quality-check` RUNS DAILY** — 305 reports over 79 distinct days — while writing nothing to
that table, so every audit reading the table as a job registry scored it as dead. Correct it wherever
it appears.

The sharp version: **the table is a log about one job, consumed as a registry of all jobs, by two
jobs that are themselves missing from it.**

Related and separately recorded: `proxy-domain-recheck` has **never run** (`KI-82`,
`last_checked_at == verified_at == 2026-07-15`); `email-reports-weekly` **stopped entirely
2026-07-27** (`KI-86`) — a job that does not run, distinct from the older defect of a job that runs
and sends nothing; fixing either leaves the other live.

### 2.3 The guard that cannot fail

`health-agent` had **no persistent output at all** — unmonitorable by construction, with a crash
indistinguishable from a clean run (`KI-84`, fixed #669). `homeFixtures.js:145` claimed
*"Guarded: `api/tests/ai-assistant-count-copy.test.js`"* for a test that **has never existed**
(`KI-93`) — in the same file whose `:28` copy implies 22 AI assistants against its own `:147` export
of 16 (`KI-94`), which is exactly what the fictional test would have caught. The v3 token audits
could only report success until #663 made them able to fail (`KI-88`).

**The generalisation worth keeping: all of these PASSED.** None failed loudly and got ignored; they
were structurally incapable of failing. When adding a guard, the first question is *"what input makes
this fail?"* — if there isn't one, it is decoration.

### 2.4 The authorised identity is not the observed identity

The proxy serves on `track.`, which matches **no row** in `managed_proxy_domains`; the single row is
`track2.`; and tenant resolution reads the **`cdn-host` header, not the browser's `Host`**
(`KI-81`). **This is not a gate bypass** — the gate hard-404s on a miss, proven by a `POST` with an
invalid `site_key` returning **401, not 404**. The consequence is narrower and worse: the DB row and
the customer-facing domain can drift indefinitely with nothing detecting it, and the verification job
monitors `track2` while `track.` carries the traffic. **Do not fix by editing the row** — which
hostname is authoritative is an open decision. Full evidence is in #666.

Same shape at the CI layer: a **stacked PR gets no CI at all** (`KI-87`) — `ci.yml:16-17` triggers
`pull_request` on `main` and `feat/home-v14` only, and the check that is *absent* does not announce
itself the way a red one does.

## 5. Method notes added this session

### 5.1 Install before baselining

See §3.1. Now a standing step, not a judgment call.

### 5.2 ⚠️ A grep that finds nothing has TWO explanations, and "absent" is only one of them

This bit **three times in one session**, and every instance would have produced a wrong published
conclusion:

| What was searched | Why it returned zero | The truth |
|---|---|---|
| `-0.03em` in `design.md` | The doc uses a **Unicode minus (U+2212)**, not an ASCII hyphen | The spec **is** there, at `:312` |
| `pv_limit integer DEFAULT` in the baseline migration | The column is **quoted** in the DDL — `"pv_limit"` | It **is** there, at `:900`, exactly as cited |
| `role="button"` in `Accordion.tsx` | Genuinely absent | Really absent — the claim was wrong (§3.2) |

**Two of three zero-hit greps were the grep's fault, not the code's.** The same class as reading a
`getaddrinfo NXDOMAIN` as "the service is down". **Before reporting a citation as unresolvable,
search for the identifier a second way** — different quoting, different character, a substring of the
symbol. Report the miss, not the conclusion.

### 5.3 Verify a branch base by CONTENT, not `merge-base`

After a squash-merge, `merge-base` lies. Check for a marker the base commit introduced — this session
checked #664's `.v3-band-ruled` and `.v3-plan-blurb`. Standing habit on every branch.
