## 4. 🔴 NEW — RLS disabled on three staging tables, with full `anon` DML

**Status of the originating dispatch: it was never received.** A dispatch reportedly asked for a repo
grep of these three tables to determine backend-only vs client-side exposure. No such dispatch arrived,
so there was no prior result to report. **The investigation was run fresh while writing this file**, and
it found more than the grep alone would have.

### What the code says

`public.paas_subdomain_blocklist` · `public.disposable_email_domains` · `public.usage_email_log`

**All three are backend-only. Zero client-side references** — nothing in `dashboard/src/` or
`marketing/src/` touches any of them.

- **`paas_subdomain_blocklist`, `disposable_email_domains`** — read only by the Postgres trigger
  function `enforce_free_tier_abuse_guards()`, which is **`SECURITY DEFINER`**
  (`supabase/migrations/20260522000002_free_tier_abuse_guards.sql:48-51`, trigger at `:101-104`).
  There is no JS reader; the free-tier abuse guard is **enforced at the DB layer**, and
  `api/lib/abuse-guards.js` is vestigial.
- **`usage_email_log`** — read/written only by `api/jobs/usage-threshold-emails.js:147,174` through the
  **service-role** client.

Both `SECURITY DEFINER` and `service_role` **bypass RLS**, so enabling RLS on all three would break
nothing.

### What the live databases say — and prod and staging **differ**

| | RLS enabled | `anon` / `authenticated` grants |
|---|---|---|
| **prod** (`zxjjjsipafojhzkkumvh`) | ✅ **true** (all three) | SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER |
| **staging** (`nrsvpwzekfrdrzkoecfk`) | 🔴 **false** (all three) | SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER |

**Prod is protected** — RLS on with no policies is default-deny for `anon`/`authenticated`, which is
correct here since only the `SECURITY DEFINER` trigger and `service_role` need access.

**Staging is genuinely exposed, not advisory noise.** RLS off *plus* full DML to `anon` means anyone
holding the staging anon key can `DELETE` or `TRUNCATE` the two abuse blocklists — which **defeats the
free-tier abuse guard entirely**, since the trigger's checks pass trivially against empty tables — and
can read or forge `usage_email_log` rows to suppress or duplicate threshold emails.

**No customer data is at risk** (staging only, and none of the three holds customer PII). The real
issues are that staging's abuse guard is defeatable, and that this is live schema drift of exactly the
kind CLAUDE.md §8 warns about — prod tighter than staging.

### Recommended fix

A forward-only migration enabling RLS on all three, applied to **staging** (prod already has it):

```sql
alter table public.paas_subdomain_blocklist  enable row level security;
alter table public.disposable_email_domains  enable row level security;
alter table public.usage_email_log           enable row level security;
```

No policies needed — default-deny is the desired end state, and both real readers bypass RLS. Per §8,
CC writes the migration file; the founder reviews and hand-applies. **Not yet filed as an issue.**
